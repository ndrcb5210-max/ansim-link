# 6단계 — 출시 준비

작업일: 2026-10-25 · 브랜치: `feature/06-release-prep`

이 단계에는 새 기능이 거의 없다. 한 일은 **빌드를 출시용으로 만들고, 앱이 하는 일을
글로 적고, 하지 않은 것을 하지 않았다고 적는 것**이었다. 그런데 글을 적는 동안 코드에
있던 사실관계 오류가 두 개 나왔다(아래 '막힌 점' 3·4번). 설명을 쓰다 보니 틀린 것이
드러난 셈이다.

## 한 일

### 릴리스 서명 — 값이 없으면 멈추지 않고 건너뛴다

환경 변수 네 개(`ANSIM_KEYSTORE_PATH`, `ANSIM_KEYSTORE_PASSWORD`, `ANSIM_KEY_ALIAS`,
`ANSIM_KEY_PASSWORD`)가 **모두** 있을 때만 `release` 서명 설정을 만든다.

값이 없을 때 빌드를 실패시키지 않는 쪽을 골랐다. CI 의 `assembleDebug` 와 이 저장소를
받은 다른 사람의 로컬 빌드가 키 없이 돌아야 한다. 대신 상태를 나눠서 알린다.

| 상태 | 반응 |
| --- | --- |
| 네 개 다 없다 | 안내(`lifecycle`) 한 줄. 평소 상태라 경고로 띄우면 디버그 빌드마다 울린다 |
| **일부만 있다** | **경고**(`warn`). 거의 틀림없이 오타나 시크릿 누락이다 |
| 경로가 가리키는 파일이 없다 | 경고. 비밀번호는 로그에 찍지 않고 경로만 적는다 |

'일부만 있다'를 따로 가른 것이 이 설계의 요점이다. 네 개를 한 덩어리로 보고 '하나라도
없으면 조용히 건너뛰기'로 하면, 시크릿 이름을 하나 잘못 적은 릴리스 빌드가 **성공한
것처럼** 끝난다.

키스토어 경로는 `rootProject` 기준으로 푼다. `app/` 기준으로 풀면 같은 상대 경로가
명령을 어디서 실행했는지에 따라 다른 파일을 가리킨다.

### AAB 는 서명하지 않아도 이름이 같다

이 단계에서 가장 쓸모 있었던 발견이다. 확인해 보니

| 산출물 | 서명 없이 빌드하면 |
| --- | --- |
| APK | `app-release-unsigned.apk` — 이름으로 바로 안다 |
| **AAB** | **`app-release.aab`** — 서명한 것과 **이름이 같다** |

직접 열어서 확인했다. 서명하지 않은 AAB 에는 `META-INF/*.RSA` 와 `*.SF` 가 없고,
서명한 AAB 에는 있다. 파일 이름·크기만 보면 구분되지 않는다.

그래서 **빌드를 깨지 않기로 한 결정의 대가**가 생긴다. 환경 변수에 오타가 있으면
경고 한 줄이 흘러가고 서명 안 된 AAB 가 아티팩트로 올라간다. 그걸 Play 에 올리려다
알게 되는 건 몇 단계 뒤다.

그래서 릴리스 워크플로가 **결과물을 직접 본다.**

```yaml
jarsigner -verify -strict "$aab"
```

경고를 내는 쪽(빌드 스크립트)과 멈추는 쪽(워크플로)을 나눴다. 로컬 빌드는 키 없이도
돌고, 릴리스 경로에서는 서명 안 된 것이 지나가지 못한다.

### R8 — keep 규칙보다 '없어도 되는 이유'를 적었다

`isMinifyEnabled = true` 는 1단계부터 켜져 있었는데 **릴리스 빌드를 한 번도 돌려 본 적이
없었다.** 이번에 처음 돌렸고, R8 은 깨끗하게 통과했다. `missing_rules.txt` 가 나오지
않았다(= 없는 클래스에 대한 경고가 없었다).

추가로 넣은 keep 규칙은 **하나도 없다.** 대신 `proguard-rules.pro` 에 리플렉션이 있을 수
있는 자리를 하나씩 확인한 결과를 적었다.

| 확인한 것 | 결론 | 근거 |
| --- | --- | --- |
| 매니페스트 구성 요소(Activity·Service·Receiver) | 필요 없음 | AGP 가 병합된 매니페스트로 keep 규칙을 만든다 |
| `SafetyMessageWorker` | 필요 없음 | work-runtime AAR 안 `proguard.txt` 가 `-keepnames class * extends androidx.work.ListenableWorker` + 생성자 keep 을 넣는다. 클래스는 `OneTimeWorkRequestBuilder<SafetyMessageWorker>` 에서 코드로 참조된다 |
| Room | 필요 없음 | room-runtime AAR 의 `-keep class * extends androidx.room.RoomDatabase` 가 생성된 `_Impl` 을 잡는다 |
| Firestore 필드 이름 | 필요 없음 | `toObject()`/POJO 매핑을 쓰지 않는다. `get("필드이름")` 으로 문자열로 읽는다 |
| enum 을 이름으로 되살리는 코드 | 없음 | `valueOf`·`Class.forName` 을 쓰는 곳이 없다. 저장하는 enum 은 `name` 대신 직접 정한 `key` 를 쓴다 |
| Play Billing | 필요 없음 | 순수 자바 + consumer 규칙 |

AAR 의 consumer 규칙은 **추측하지 않고 꺼내서 읽었다.**

```
$ unzip -p work-runtime-2.12.0.aar proguard.txt
-keepnames class * extends androidx.work.ListenableWorker
-keepclassmembers public class * extends androidx.work.ListenableWorker {
    public <init>(...);
}
```

**'없어도 되는 이유'를 글로 남긴 까닭.** 이 앱에서 R8 이 잘못 지우면 평소에는 아무 증상이
없다. 알림 리스너·포그라운드 서비스·WorkManager 작업은 **재난문자가 올 때만** 돌아간다.
릴리스 빌드에서 그게 깨져 있어도 다음 재난까지 모른다. 그러니 '아마 되겠지'로 둘 수 없고,
확인한 사실을 다음 사람이 다시 확인할 수 있게 적어 두는 쪽이 맞다고 봤다.

덧붙여 R8 이 지운 양: `usage.txt` 의 클래스 단위 줄이 31,436줄이고, 그중 11,647줄은
`클래스:` 꼴(클래스는 남기고 멤버만 지운 것)이다. 즉 통째로 지운 클래스가 약 19,800개다.
디버그 APK 는 22.6MB, 릴리스 AAB 는 8.5MB 다(AAB 와 APK 는 담는 것이 달라 크기를
그대로 비교할 수는 없다).

### 공개 문서 — 사본을 사람이 만들지 않는다

약관을 공개해야 한다. Play Console 이 처리방침과 계정 삭제 안내를 **URL 로** 받기 때문이다.

문제는 같은 글이 세 군데 있게 된다는 것이다.

```
docs/legal/*.md  (원본)
  → app/src/main/res/raw/legal_*.md   (앱 화면, copyLegalDocuments 가 복사)
  → docs/site/*.md                    (공개 사이트, 이번에 추가)
```

2단계에서 앱 쪽은 이미 복사로 해결해 두었다('같은 글을 두 군데 두면 반드시 어긋난다').
사이트 쪽도 같은 방법으로 했다. `./gradlew syncSiteDocuments` 가 원본에 Jekyll 앞머리와
'만들어진 파일' 표시를 붙여 `docs/site/` 에 쓴다. 사람은 `docs/legal` 만 고친다.

그런데 복사는 **잊을 수 있다.** 약관을 고치고 사이트를 다시 만들지 않으면 앱에 적힌
처리방침과 공개된 처리방침이 다른 상태가 된다. 그건 단순한 버그가 아니다.

그래서 단위 테스트를 달았다(`SiteDocumentsTest`, 4개).

| 보는 것 | 왜 |
| --- | --- |
| 사본 본문이 원본과 글자까지 같은가 | 복사를 잊은 것을 잡는다 |
| 앞머리의 `title`·`permalink` 가 맞는가 | 페이지 이름을 바꿔 링크가 깨진 것을 잡는다 |
| `docs/legal/*.md` 가 **전부** 사이트에 있는가 | 약관을 새로 만들고 공개를 잊은 것을 잡는다 |
| 첫 화면이 네 문서를 다 가리키는가 | 사이트에 올려 두고 링크를 안 단 것을 잡는다 |

`testDebugUnitTest` 에 들어 있어서 단계별 검사와 CI 에서 같이 돌아간다. 저장소 경로는
Gradle 이 시스템 속성(`ansim.repoRoot`)으로 넘겨 준다 — 작업 디렉터리는 실행하는 쪽에
따라 달라서 기댈 수 없다.

줄바꿈은 LF 로 통일하고 테스트도 양쪽을 정규화한다. `.gitattributes` 의 `* text=auto`
때문에 윈도우 작업 폴더의 원본이 CRLF 라서 그냥 비교하면 늘 틀린다.

**`docs/` 전체를 공개하지 않았다.** GitHub Pages 의 브랜치 배포 방식은 사이트 뿌리를
`/` 또는 `/docs` 중에서만 고를 수 있다. `/docs` 를 뿌리로 하면 devlog·prompts·screenshots
까지 사이트가 되고, 처리방침 URL 옆에 개발 기록이 같이 공개된다. 그래서 Actions 로
`docs/site` 만 빌드한다(`pages.yml`). **Pages 를 켜지 않았으므로 실행해 본 적은 없다.**

### Play Console 제출 자료 (`docs/play/`)

다섯 문서를 썼다. 전부 초안이고 **아무것도 제출하지 않았다.**

| 문서 | 이 단계에서 신경 쓴 것 |
| --- | --- |
| `store-listing.md` | 짧은 설명 44자에 '언제·누구와·무엇을·얼마나'를 넣었다. 고르지 **않은** 안과 이유도 적었다 |
| `data-safety.md` | 스키마를 훑어 기기 밖으로 나가는 것만 적었다. 모호한 자리는 '넓게 알리는 쪽'으로 골랐다 |
| `permissions-declaration.md` | 선언서 문구를 앱의 실제 문자열에서 그대로 옮겼다. 영상 대본 30초 |
| `app-content.md` | 대상 연령 구간 문제(아래 5번), 심사용 계정과 심사자 안내문 |
| `closed-testing-plan.md` | 테스터 12명·14일. 모집 문구, 피드백 폼, 프로덕션 신청서 답변 틀 |

**스토어 설명의 첫 덩어리를 '먼저 알려 드립니다'로 잡았다.** 보통은 기능 자랑이 먼저
오는 자리인데, 이 앱에서 가장 중요한 정보는 '못 할 수도 있다'다. 재난 상황에서 이 앱을
믿고 기다리는 것이 제일 나쁜 결과이기 때문이다. 그 덩어리에 세 가지를 적었다 —
감지를 보장하지 않음, 공공기관 앱이 아님, 동의한 사람만 공유.

**데이터 보안에서 '공유'를 예로 적었다.** Play 는 '사용자가 직접 시작했고 사용자가
예상할 수 있는 전달'을 공유에서 뺄 여지를 준다. 이 앱의 위치 전달이 거기에 해당할 수
있다. 그래도 예로 적는다. 위치정보법은 같은 일을 분명히 제3자 제공으로 보고(제19조)
그래서 따로 동의받고 매회 통보하고 기록을 남기게 되어 있다. 한쪽에서는 제3자 제공이고
다른 쪽에서는 '공유 아니요'인 상태를 만들고 싶지 않았다. **적게 알리는 쪽으로 틀리면
사용자가 모르는 일이 생기고, 넓게 알리는 쪽으로 틀리면 사용자가 더 알게 된다.**

### 출시 체크리스트 (`docs/RELEASE_CHECKLIST.md`)

저장소 안에서 끝낼 수 없는 일만 모았다. **체크박스가 전부 비어 있다.** 그게 맞는 상태다.

기한이 있는 것을 맨 앞에 뒀다. 대상 API 36 과 Billing 8 이상의 **연장 신청 기한이 둘 다
2026-11-01** 이다. 지금 `targetSdk 36`·`billing 9.1.0` 이라 이미 충족이고 신청할 일이
없다. 되돌리면 그때 걸린다.

Play 앱 서명 항목을 따로 뺐다. 새 앱은 AAB 를 올리면 Play 앱 서명에 자동 등록되고,
사용자 기기에 설치되는 APK 는 **Google 이 보관하는 앱 서명 키**로 서명된다. Firebase 에
업로드 키 지문만 등록해 두면 **Play 로 설치한 빌드에서만 Google 로그인이 실패한다.**
개발 중에는 잘 되다가 테스터 빌드에서만 안 되는, 원인을 찾기 어려운 증상이다.
지문 기록란을 만들어 두었다(근거: Play Console 고객센터 answer/9842756).

## 막힌 점

### 1. 환경 변수를 설정할 수 없는 작업 환경에서 서명을 어떻게 확인했나

이 단계의 핵심 산출물이 '환경 변수로 서명하기'인데, 작업 환경이 **환경 변수 설정과
`keytool` 실행을 허용하지 않았다.** `ANSIM_KEYSTORE_PATH=... ./gradlew`,
`$env:ANSIM_...=...`, `env VAR=... ./gradlew` 가 모두 막혔고 새 키스토어도 만들 수 없었다.

우회하지 않고 확인할 수 있는 것만 확인했다.

| 확인한 것 | 방법 | 결과 |
| --- | --- | --- |
| 환경 변수가 **없을 때** 건너뛰고 안내만 내는가 | 그냥 `bundleRelease` | 통과. 안내 한 줄 뒤 **서명 없는** AAB |
| R8 을 켠 `bundleRelease` 가 AAB 를 만드는가 | 같은 빌드 | 통과 (8.5MB, `missing_rules.txt` 없음) |
| 키스토어를 주면 AAB 가 **정말 서명되는가** | AGP 의 주입 서명 속성(`-Pandroid.injected.signing.*`)에 기존 디버그 키스토어(저장소 밖, 던져 버릴 키)를 넘겨 빌드 | 통과. `META-INF/ANDROIDD.RSA` 생김 |

**확인하지 못한 것: `System.getenv` → `signingConfig` 로 값이 흘러가는 마지막 한 칸.**
그 칸은 `release.yml` 이 처음 돌 때 검증된다. 그래서 그 워크플로에 `jarsigner -verify`
단계를 넣었다 — 그 칸이 틀리면 '경고 한 줄 + 서명 안 된 AAB' 로 조용히 지나가는데,
결과물을 직접 보면 반드시 걸린다.

지시문이 말한 '`%TEMP%` 에 임시 키를 만들어 시험'은 하지 못했다. `keytool` 이 실행
승인을 받지 못했고 이 세션에서는 승인을 받을 길이 없었다. 대신 **이미 있던 디버그
키스토어**(`~/.android/debug.keystore`, 저장소 밖, 비밀번호가 공개된 던져 버릴 키)를
썼다. 성격은 같다 — 저장소에 들어가지 않는 임시 키다.

### 2. R8 을 켜 두고 한 번도 돌리지 않았던 것

1단계부터 `isMinifyEnabled = true` 였는데 `assembleRelease`·`bundleRelease` 를 돌린 적이
없었다. 5단계까지의 검사 명령이 `lint testDebugUnitTest assembleDebug` 라서 **릴리스
경로는 한 번도 지나가지 않았다.**

다행히 처음 돌려서 바로 통과했다. 하지만 '다섯 단계 동안 아무도 안 본 코드 경로가
있었다'는 사실 자체가 교훈이다. 깨졌으면 5단계 분량의 변경 중 어디서 깨졌는지 찾아야
했을 것이다. CI 에 릴리스 빌드를 넣는 것은 아래 '남은 일'에 적었다.

### 3. 매니페스트 주석과 실제 권한이 달랐다 — `RECEIVE_BOOT_COMPLETED`

데이터 보안 문서를 쓰려고 병합된 릴리스 매니페스트를 열어 권한 목록을 뽑았다.

```
$ grep -o 'uses-permission android:name="[^"]*"' .../packaged_manifests/release/AndroidManifest.xml
...
uses-permission android:name="android.permission.RECEIVE_BOOT_COMPLETED"
```

`app/src/main/AndroidManifest.xml` 에는 이렇게 적혀 있다.

> `RECEIVE_BOOT_COMPLETED` 는 넣지 않는다. 재부팅 뒤 공유를 되살리지 않는다.

**둘 다 사실이다.** 우리는 선언하지 않았고, WorkManager 가 자기 매니페스트에서 선언해
병합돼 들어온다(재부팅 뒤 예약된 작업을 다시 등록하려고 쓴다). 방침도 지켜진다 —
재부팅 뒤 공유를 되살리는 코드는 없다.

그런데 **'우리가 선언하지 않았다'와 '앱에 그 권한이 없다'는 다른 말이다.** 스토어의
권한 목록과 설치 화면에는 병합된 결과만 보인다. 사용자가 보는 것과 우리가 주석에 적은
것이 다른 셈이다. `USE_BIOMETRIC`·`USE_FINGERPRINT`(androidx.credentials)도 같은 경우다.

주석을 고치지는 않았다(그 문장은 '우리 매니페스트에 적지 않는다'는 뜻으로 맞다).
대신 병합된 권한 전체를 어디서 왔고 무엇에 쓰는지 표로 적었다
(`docs/play/permissions-declaration.md` 5항). 질문이 오면 그 표로 답한다.

### 4. 심사자 안내문에 없는 버튼을 적을 뻔했다

'테스트 발동' 버튼으로 발동 흐름을 보여 주면 되겠다고 안내문을 썼다가 확인해 봤다.
`AnsimLinkApp.kt` 가 설정 화면의 디버그 항목을 `showDebugEntries = BuildConfig.DEBUG` 로
가린다. **릴리스 빌드에는 그 버튼이 없다.** 5단계에서 가짜 결제 저장소를 `src/debug/`
소스셋에 둔 것과 같은 결정의 결과다.

심사자가 재난문자를 기다릴 수는 없으므로, 안내문을 **홈 화면의 '지금 공유'** 로 바꿨다.
그 경로도 `ShareController` 를 지나므로 위치 공유 기능 자체는 그대로 확인된다.
'재난문자 감지 → 알림' 장면은 시연 영상이 대신한다.

하마터면 '안내문대로 해 봤는데 그런 버튼이 없다'는 심사 거절을 받을 일이었다.

### 5. Play 의 연령 구간에 '만 14~15세'가 없다

이 앱은 가입 때 만 14세 이상을 확인한다(위치정보법 제25조, 개인정보 보호법 제22조의2).
그런데 Play 의 대상 연령 구간은 `만 13~15세` 다. 그 구간을 고르면

- 만 13세도 대상으로 선언하는 셈이 되어 앱의 가입 요건과 어긋나고,
- Google Play **Families 정책**(아동 대상 앱) 요건이 따라붙는다.

한국 법에 맞춘 경계(14세)가 Play 의 경계(13세, 16세)와 어긋나는 자리다.
**만 16세 이상으로 선언하는 쪽**을 골랐다. '아동 대상 앱이 아니다'(CLAUDE.md 원칙 7)를
분명히 하는 쪽이 맞다고 봤다. 법이 허용하는 만 14~15세는 가입은 되지만 스토어 대상
연령에는 포함되지 않는다.

이게 정책상 문제가 되는지는 **확인하지 못했다.** 반대 방향(선언이 낮고 요건이 높은 것)
보다는 안전하다고 보지만, 심사에서 지적되면 가입 요건을 16세로 올리는 것이 다음 수다.
`docs/play/app-content.md` 에 그 판단과 대안을 적어 두었다.

### 6. 법령 확인의 한계 — 확정하지 못하고 '물어볼 곳'만 적었다

두 가지를 확정하지 못했다.

**위치기반서비스사업 신고(제9조)만으로 되는지, 위치정보사업 등록(제5조)도 필요한지.**
쟁점은 '단말이 준 위치를 서버를 거쳐 다른 이용자에게 전달하는 것'이 제5조의 위치정보
사업에 해당하는지다. 이 앱은 직접 측위하지 않는다(Fused Location Provider 가 준 값을
쓴다). 해석이 갈릴 수 있는 자리라 공식 문서만으로 결론을 내지 않았다.
체크리스트에 **위치정보지원센터(lbsc.kr, 02-588-0185)** 와 물어볼 네 가지, 결과 기록란을
두었다.

**통신판매업 신고.** 전자상거래법 제12조 단서와 공정거래위원회 고시 제2022-4호가
'직전년도 거래 50회 미만 또는 간이과세자'를 면제한다. 그런데 Google 이 결제를 대행하는
앱 안 구독에서 **누가 통신판매업자인지**가 쟁점이고, 거래 횟수를 Play 결제 건수로 세는지도
모른다. '확인 필요'로 두고 물어볼 곳을 적었다.

추측으로 '신고 대상 아님'이라고 적는 것이 가장 위험하다. 그 문장은 체크리스트에서
'확인 완료'처럼 읽힌다.

### 7. 사람 검토로 받은 정정 — 제16조②는 기간을 정하지 않는다

지시문에 사람 검토 결과가 함께 왔다. 2단계 약관 초안과 계정 삭제 화면이

> 위치정보법 제16조에 따라 확인자료를 **6개월** 보관합니다

라고 적어 두었는데, 제16조②는 확인자료를 **자동으로 기록·보존하라고만** 정하고
**기간은 정하지 않는다**(시행령 2026-02-10 시행본에도 없다). 기간은 제18조①4호·
제19조①4호에 따라 **약관에 적는 사항**이다.

즉 **법에 없는 기간을 법 근거로 제시**하고 있었다. 틀린 방향도 고약하다 — 사용자에게
'법이 그렇게 정해서 어쩔 수 없다'로 읽힌다.

근거와 기간을 나눠 적는 것으로 고쳤다.

```
근거: 위치정보법 제16조제2항에 따라 자동으로 기록·보존한다
기간: 제18조①4호·제19조①4호에 따라 이 약관으로 정하며, 180일로 한다
```

고치면서 **숫자도 맞췄다.** 코드는 180일에 지우는데(`RETENTION_MILLIS`) 문서는 '6개월',
제공 기록 화면은 '180일'이라고 말하고 있었다. 6개월과 180일은 같은 기간이 아니다.
전부 **180일**로 통일했다.

그리고 화면 문구가 숫자를 들고 있지 않게 바꿨다. 계정 삭제 화면의 문구에는 '6개월'이
박혀 있었다. 이제 두 화면 모두 `ProvisionRecordRepository.RETENTION_MILLIS` 에서
일수를 받아 간다. 상수를 고치면 화면은 저절로 따라오고, 약관만 사람이 고치면 된다.

| 자리 | 전 | 후 |
| --- | --- | --- |
| 약관 제6조 | 제16조②에 따라 6개월 | 근거(제16조②) / 기간(약관, 180일)을 나눠 적음 |
| 처리방침 3항 | 제16조②에 따라 6개월 이상 | 같음 + 제21조의2 항목을 표로 정리 |
| 계정 삭제 안내 | 제16조② / 6개월 | 근거·기간 두 칸으로 나눔 |
| 계정 삭제 화면 | 문구에 '6개월' 박음 | 상수에서 일수를 받음 |
| 제공 기록 화면 | '%d일 동안 보관' | '제16조②에 따라 자동으로 남기며, 약관에서 정한 기간인 %d일' |

4단계 devlog 에도 같은 오류가 있어서 정정 표시를 달았다.

### 8. 그 밖에 고민한 것

- **`pages.yml` 의 액션 버전.** `configure-pages@v5`, `jekyll-build-pages@v1`,
  `upload-pages-artifact@v3`, `deploy-pages@v5` 를 썼다. 기억으로 적지 않고
  `actions/starter-workflows` 의 `pages/jekyll-gh-pages.yml` 을 확인해 맞췄다
  (이 저장소의 다른 워크플로가 `checkout@v7` 을 쓰고 있어서 체크아웃만 v7 로 뒀다).
- **release.yml 에서 `secrets` 를 `if:` 에 쓰지 못한다.** GitHub 의 컨텍스트 표에
  step 의 `if:` 에는 `secrets` 가 없다. job 의 `env:` 에서는 쓸 수 있어서 거기서
  참·거짓으로 바꿔 두고 `env.HAS_SIGNING_SECRET != 'true'` 로 본다. 비밀 값 자체를
  job env 에 올리지 않은 것도 일부러다 — 쓰는 단계에서만 넣는다.
- **자리표시자 `google-services.json` 으로 만든 AAB.** Play 에 올리면 Firebase 에 붙지
  못해 로그인·그룹·푸시가 전부 안 된다. 그런데 빌드는 성공한다. 그래서 워크플로가
  시크릿이 없을 때 `::warning` 으로 '올리지 말 것'을 남긴다. 서명 시크릿이 없을 때는
  경고가 아니라 **빌드 전에 멈춘다** — 서명 안 된 AAB 는 아예 쓸 데가 없기 때문이다.
- **키스토어를 `RUNNER_TEMP` 에 복원한다.** 작업 폴더에 두면 나중에 단계를 하나 더했을 때
  아티팩트에 담기거나 커밋될 수 있다. 끝에서 `rm -f` 로 지운다(러너는 버려지지만
  명시해 두는 편이 낫다).
- **스크린샷을 Play 에 그대로 쓸 수 있는지 모른다.** `docs/screenshots/` 의 PNG 는
  Robolectric 화면 크기에서 나온 것이라 Play 의 비율·최소 크기 요건을 만족하는지
  파일별로 확인하지 않았다. 아이콘(512×512)과 그래픽 이미지(1024×500)는 **아예 없다.**
- **UGC 신고 기능이 없다.** 안심 메시지는 초대 코드로 들어온 자기 그룹 구성원에게만
  가므로 모르는 사람이 보낼 길이 없다. Play 의 UGC 정책이 이 앱에 적용되는지는
  확인하지 못했다. 적용된다면 '그룹에서 내보내기'를 만들어야 한다 — 지금은 당사자가
  '동의 철회'로 나가는 것만 된다.
