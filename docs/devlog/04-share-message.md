## 한 일

### 위치 공유 포그라운드 서비스

`LocationShareService` (`foregroundServiceType="location"`). 위치는 이 서비스가 돌고
있을 때만 수집하고, 그동안 상시 알림이 항상 보인다.

시작 경로가 세 가지인데(알림의 '공유 시작' / 앱의 '지금 공유' / 자동 시작) 전부
`ShareController` 하나를 지나게 했다. 백그라운드 시작 제한을 다루는 코드가 세 군데로
흩어지면 한 군데를 고칠 때 나머지를 빼먹는다.

**포그라운드로 올리는 것을 제일 먼저 한다.** 상시 알림 없이 위치를 수집하는 순간이
있어서는 안 되고(원칙 2), Android 는 서비스 시작 뒤 짧은 시간 안에 `startForeground` 를
부르지 않으면 앱을 죽인다. 동의 확인·제공 기록·위치 요청은 모두 그 다음이다.

### 동의 확인은 시작할 때 한 번이 아니다

이 단계에서 가장 신경 쓴 부분이다. `SharePolicy.decide()` 로 시작을 막는 것만으로는
모자란다. 60분짜리 세션 중간에 사용자가 '일시중지'를 누르면 그 순간부터 멈춰야 한다
(원칙 1: 즉시 반영).

그래서 위치를 쓸 때마다 Firestore 에서 동의 상태를 **다시 읽어** 거른다.

```kotlin
val refreshed = targets.mapNotNull { target -> /* 지금 상태로 갱신 */ }
targets = SharePolicy.sharingTargets(refreshed)
if (targets.isEmpty()) {
    handleStop(StopCause.ConsentChanged)   // 마지막 위치까지 바로 지운다
    return@withLock
}
```

60초에 한 번이라 읽기 비용이 크지 않다. 동의가 바뀌어 멈춘 경우에는 마지막 위치를
24시간 두지 않고 **바로** 지운다.

규칙에서도 같은 것을 막는다. `firestore.rules` 의 `locations` 쓰기 조건이 구성원 문서를
읽어 `consent.location == true && paused == false` 를 확인한다. 앱 코드에 버그가 있어도
동의 없는 위치는 서버에 올라가지 못한다.

### 쓰기를 줄이는 규칙과 '가만히 있는 사람' 문제

`LocationWriteRule` 은 60초 간격 · 50m 이상일 때만 쓴다(CLAUDE.md). 거리는 하버사인으로
직접 계산한다. `Location.distanceTo` 를 쓰면 Robolectric 이 필요한데, 순수 Kotlin으로
두면 단위 테스트가 쉽다. 50m 판정에 하버사인의 0.5% 오차는 25cm 라 문제가 없다.

그런데 '50m 이상 움직였을 때만'으로는 모자랐다. 집에 가만히 있는 사람은 세션 내내 첫
위치 한 건만 남는다. 보는 쪽에서 **'앱이 죽은 건가, 정말 가만히 있는 건가'를 구분할 수
없다.** 재난 상황에서 이 구분은 중요하다. 그래서 5분마다 한 번은 움직이지 않아도 쓴다.

쓰기 건수를 테스트로 박아 두었다.

| 상황 | 60분 세션 쓰기 |
| --- | --- |
| 계속 가만히 있음 | 13건 (첫 1 + 하트비트 12) |
| 60초마다 100m 씩 이동 | 61건 |

구성원 3명이 모두 움직여도 183건이라, 무료 요금제 하루 2만 건 안에서 100세션쯤 된다.

정확도가 500m 보다 나쁜 위치는 버린다. 실내·지하에서 Wi-Fi 기반 위치가 수백 미터
오차로 오는데, 그 값을 쓰면 가만히 있는 사람이 지도에서 튀어 다니고 '50m 이상 움직였다'로
잡혀 쓰기까지 늘어난다.

### 위치 제공 기록 (위치정보법 제19조③)

공유를 시작할 때마다 '누구에게·언제·무슨 목적으로' 제공했는지 남긴다. 기기(Room)와
서버(Firestore) 양쪽에 같은 내용을 둔다.

**좌표를 담지 않는다.** 이게 핵심이다. 좌표는 세션이 끝나면 마지막 1건만 남기고 24시간
뒤 지워야 하는데(원칙 4), 제공 내역은 제16조② 때문에 6개월 남아야 한다. 보관 기간이
다른 두 가지를 같은 자리에 두면 둘 중 하나는 반드시 어긋난다.

서버에 쓸 때 **제공 내역을 먼저 쓰고 그 다음에 `sharing.active` 를 켠다.** 순서를
거꾸로 하면 기록 쓰기가 실패했을 때 '기록 없이 제공되는' 상태가 된다. 반대 순서면
최악의 경우 '기록은 있는데 제공은 안 된' 상태라 이쪽이 안전하다. 끌 때는 반대로
`active` 를 먼저 내린다(줄이는 방향은 언제나 즉시).

### 자동 시작 모드

설정에서 켤 때 순서를 지킨다. 명시적 공개 → 위치 권한 → 배경 위치 권한(설정 화면 이동).
`AutoStartFlow.nextStep()` 이 단계를 정하고 화면은 **그 단계에 맞는 것 하나만** 보여
준다. 세 개를 다 보여 주면 사용자가 공개 화면을 건너뛰고 권한 버튼을 먼저 누를 수 있다.

저장된 스위치 값만 믿지 않는다. 사용자가 시스템 설정에서 '항상 허용'을 '앱 사용 중에만'
으로 내릴 수 있으므로, 발동할 때마다 권한을 같이 보고 모드를 정한다
(`AutoStartFlow.effectiveMode`). 권한이 빠졌으면 저절로 기본 모드로 돌아간다.

자동 시작이 막히면(백그라운드 시작 제한) **조용히 포기하지 않고** '눌러서 시작' 알림으로
바꾼다. 사용자가 알림을 눌러 시작하는 것은 예외로 허용되기 때문이다.

### 안심 메시지

`SafetyMessageWorker`(WorkManager)가 `groups/{gid}/alerts/{id}` 문서를 만든다.
**앱은 FCM 을 직접 보내지 않는다.** 발송에는 서버 자격 증명이 필요하고, 그 키를 앱에
넣으면 APK 를 뜯어 꺼낸 누구나 아무에게나 푸시를 보낼 수 있다.

코루틴이 아니라 WorkManager 로 한 이유: 발동은 재난 상황에 일어난다. 그때 네트워크가
끊겼다 붙거나, 알림 버튼을 누른 직후 사용자가 앱을 닫거나, 시스템이 프로세스를 거둬 갈
수 있다. 코루틴만 띄우면 프로세스가 죽는 순간 사라진다.

**일시중지한 그룹에는 메시지도 보내지 않는다.** 메시지 자체에는 위치가 없지만,
'일시중지'를 누른 사람은 이 그룹에 내 소식을 보내지 않겠다는 뜻으로 눌렀을 것이다.
위치만 멈추고 메시지는 계속 가면 사용자가 예상한 것과 다르게 동작한다.

### 서버 (`functions/`)

TypeScript 2세대 함수 네 개. **배포하지 않았다**(Blaze 요금제 필요).

| 함수 | 하는 일 |
| --- | --- |
| `onAlertCreated` | alerts 문서가 생기면 그룹 구성원에게 FCM(보낸 사람 제외) |
| `onShareStarted` | `members.sharing.active` 가 false→true 로 바뀐 순간만 알림 |
| `cleanupExpiredLocations` | `expiresAt` 지난 위치 삭제 + 멈춘 `sharing.active` 끄기 (매시) |
| `cleanupOrphanLocations` | `expiresAt` 이 **없는** 위치 정리 (매일) |

'누구에게 보낼지 / 무엇을 보낼지 / 무엇을 지울지'를 `src/messages.ts` 의 순수 함수로
떼어 두었다. 그래서 **에뮬레이터 없이** `node --test` 로 33개를 돌린다.
`firebase-functions-test` 통합 테스트는 넣지 않았다. 느리고 CI 에서 깨지기 쉬운데
그것으로 더 확인할 수 있는 것은 '배선이 맞는지'뿐이고, 배선은 어차피 배포 뒤에 처음
검증된다.

## 고른 버전과 그 근거

1~3단계와 같은 방법으로 확인했다. AAR 의 `aar-metadata.properties` 로 `minCompileSdk` 를,
`classes.jar` 안 `META-INF/*.kotlin_module` 첫 16바이트로 Kotlin 메타데이터 버전을
직접 읽었다. (Kotlin 2.2 컴파일러는 메타데이터 2.3.0 까지만 읽는다 — 2단계 참고.)

| 항목 | 고른 버전 | minCompileSdk | 메타데이터 |
| --- | --- | --- | --- |
| androidx.work:work-runtime | 2.12.0 | 35 (minAGP 8.6.0) | 2.1.0 |
| com.google.android.gms:play-services-location | 21.4.0 | 1 | **2.3.0** |
| com.google.firebase:firebase-messaging | 25.1.3 (BoM 34.19.0 이 정함) | 1 | 1.9.0 |

셋 다 그대로 쓸 수 있었다. 1·2단계에서 애를 먹은 `minCompileSdk=37` 문제가 여기서는
없었다.

다만 **`play-services-location` 은 아슬아슬하다.** 자바 라이브러리인 줄 알았는데
`classes.jar` 안에 `kotlin_module` 이 5개 들어 있고(끌고 온 Kotlin 코드다) 전부
메타데이터 **2.3.0** 이다. Kotlin 2.2 컴파일러가 읽을 수 있는 **상한이 정확히 2.3.0** 이라
(자기 버전의 다음 마이너까지 — 2단계 참고) 지금은 통과하지만, 다음 버전에서 2.4.0 으로
올라가면 2단계의 `firebase-auth 25.0.0` 과 똑같이 컴파일이 깨진다. 그때는 21.4.0 에
묶어 두거나 Kotlin 을 올려야 한다(Kotlin 을 올리려면 AGP 9.2 와 compileSdk 37 이
따라붙는다 — 1단계 참고).

> 처음에 이 표를 '자바 라이브러리라 메타데이터 없음'으로 적었다가, 커밋 전에
> `classes.jar` 를 실제로 열어 보고 틀린 것을 알았다. `aar-metadata.properties` 만
> 보고 넘긴 탓이다. 두 가지를 **항상 같이** 봐야 한다.

지도 SDK(`play-services-maps`)는 **넣지 않았다.** API 키가 필요하고 저장소에 커밋할 수
없다(원칙 6).

## 막힌 점

### 1. 규칙 테스트 두 파일이 서로의 데이터를 지웠다 (매달린 원인일 수도)

4단계 규칙 테스트를 `share.rules.test.js` 로 따로 만들고 돌렸더니, **2단계 테스트까지**
엉뚱하게 깨졌다.

```
✖ 만든 사람만 그룹을 해산한다
  evaluation error at L141:24 for 'delete' @ L141, Null value error.
✖ 동의를 철회하면 위치를 쓸 수 없다
  Error: Expected request to fail, but it succeeded.
```

'막아야 할 쓰기가 통과했다'는 쪽이 특히 무서웠다. 규칙에 구멍이 있는 줄 알고 한참 봤다.

원인은 규칙이 아니었다. **`node --test` 는 기본으로 테스트 파일을 여러 개 동시에
돌린다.** 두 파일이 같은 에뮬레이터 DB 를 쓰고 `beforeEach` 마다 `clearFirestore()` 를
부르니, 한쪽이 다른 쪽 데이터를 지우고 다른 쪽이 그 자리에 자기 데이터를 깔았다.
'동의를 철회한 구성원'을 깔아 둔 직후에 다른 파일이 '동의한 구성원'으로 덮어쓰면
위치 쓰기가 통과한다.

`--test-concurrency=1` 로 고쳤다. 파일 머리말에 왜 그래야 하는지 적어 두었다.

작업이 25분 매달린 것도 이 상태에서 일어났다. 실패한 테스트가 에뮬레이터 연결을 붙든
채 종료되지 않았을 가능성이 있다고 보지만 **재현하지 못했다.** 고친 뒤로는 9초에 끝난다.
원인과 상관없이, 에뮬레이터를 쓰는 명령에는 전부 시간 제한을 걸었다.

### 2. 규칙 하나가 '일시중지'를 막을 뻔했다

`sharing.endsAt` 에 상한을 두었다. 이 값이 '지금 공유 중인가'의 근거라서
(`GroupMember.sharingNow`), 10년 뒤를 적어 두면 영원히 '공유 중'으로 보이게 만들 수 있다.

처음에는 이렇게 썼다.

```
return !('sharing' in request.resource.data)
    || request.resource.data.sharing.get('active', false) == false
    || request.resource.data.sharing.endsAt <= request.time.toMillis() + 185 * 60 * 1000;
```

틀렸다. **`update` 의 `request.resource.data` 는 쓰고 난 뒤의 문서 전체다.** 앱이 강제
종료되어 `sharing.active` 가 true 로 남고 `endsAt` 이 과거가 된 상태를 생각해 보자.
그 사람이 `paused` 를 바꾸려 하면, 그 쓰기에도 `sharing` 이 (바뀌지 않은 채) 들어 있어서
세 번째 조건에 걸려 **거부된다.** 사용자가 '일시중지'를 누를 수 없게 된다.
원칙 1(철회·중지는 한 번 누르면 즉시)을 정면으로 어기는 버그다.

`diff` 로 'sharing 이 **실제로 바뀔 때만**' 검사하게 고치고 그 상황을 테스트로 달았다.

```
return !request.resource.data.diff(resource.data).affectedKeys().hasAny(['sharing'])
    || request.resource.data.sharing.active == false
    || (...)
```

이 버그는 테스트를 쓰다가 찾은 게 아니라, 규칙을 다시 읽다가 '멈춘 세션이 남으면
어떻게 되지?'를 따라가 보고 찾았다. 보안 규칙은 **막는 것**만 보기 쉬운데
**막지 말아야 할 것을 막는지**도 봐야 한다.

### 3. `provisionLogs` 의 목록 조회를 막으면 공유 종료가 깨진다

제공 내역은 본인만 읽게 하려고 `allow list: if false` 를 넣었다. 다른 구성원이
'누가 언제 위치를 제공했는지' 훑을 수 있으면 그것 자체가 감시 도구가 되기 때문이다
(원칙 10).

그런데 앱이 공유를 **끝낼 때** 그 컬렉션을 조회한다.

```kotlin
.whereEqualTo(ProvisionLogs.SESSION_ID, sessionId)
.whereEqualTo(ProvisionLogs.UID, uid)
.get()   // ← list 다
```

`get` 과 `list` 를 같은 조건(`resource.data.uid == uid()`)으로 두면 해결된다.
Firestore 는 list 를 평가할 때 **질의가 그 조건을 보장하는지** 보므로, 남의 내역을
훑는 질의는 그대로 막히면서 이 경로만 열린다. 두 경우를 테스트로 달았다.

### 4. '가만히 있는 사람'과 '앱이 죽은 사람'을 구분할 수 없었다

위 '한 일'에 적은 하트비트 이야기다. 지시문과 CLAUDE.md 는 '50m 이상 움직였을 때만'
이라고만 했고, 그대로 만들면 동작은 한다. 그런데 화면에 띄워 놓고 보니
'18:05에 받음'에서 시각이 멈춘 사람이 지금 안전한지 알 수가 없었다.

5분 하트비트를 더했다. 60분 세션에 최대 12건이라 쓰기 예산에 거의 영향이 없다.
규칙을 벗어난 것이 아니라 규칙이 비워 둔 자리를 채운 것이라고 봤고,
`LocationWriteRule` 주석과 테스트에 왜 그랬는지 적어 두었다.

### 5. Room 버전 올리기

3단계는 `exportSchema = false` 에 마이그레이션 없이 갔다. 지금은 **이미 설치된 앱에
발동 기록이 쌓여 있다.** `fallbackToDestructiveMigration` 으로 밀면 사용자가 보던
기록이 사라진다. 테이블을 더하는 마이그레이션 하나를 직접 적었다.

`exportSchema` 는 여전히 false 다. 스키마 JSON 을 내보내면 그것으로 마이그레이션
테스트를 쓸 수 있는데, 그 테스트는 계측 테스트(기기 필요)라서 이 환경에서 돌릴 수 없다.
내보내 두고 검증하지 않는 쪽보다 남은 일로 적어 두는 쪽을 골랐다.

### 6. 쓰기에 실패한 위치를 기준점으로 삼으면 안 된다

`lastWritten` 을 50m 판정의 기준점으로 쓰는데, 처음에는 위치를 받을 때마다 갱신했다.
그러면 Firestore 쓰기가 실패했을 때도 기준점이 움직여서, 다음 위치가 '50m 안쪽'으로
걸려 **한참 동안 아무것도 못 보낸다.** 네트워크가 불안정한 상황에서 하필 아무것도 안
가는 셈이다. 쓰기에 성공한 것만 기준점으로 삼게 고쳤다.

### 7. 그 밖에 고민한 것

- **네트워크가 끊겨 동의 상태를 못 읽으면?** 저장된 목록으로 계속 간다. 재난 상황에서
  공유가 멈추는 것보다 이어지는 쪽이 낫다고 봤다. 반대로 결정할 수도 있는 자리라
  코드에 이유를 적어 두었다.
- **정리 작업을 어디서 돌릴 것인가.** 공유를 멈출 때 제공 기록의 종료 시각을 채우고
  `sharing.active` 를 꺼야 하는데, 이 작업은 **서비스가 선 뒤에도 끝나야 한다.**
  서비스 범위의 코루틴에 두면 `stopSelf` 와 함께 취소되어 기록이 열린 채 남는다.
  `AnsimLinkApplication.applicationScope` 를 만들어 거기서 돌린다.
- **알림 채널을 나눴다.** 발동 알림과 공유 중 상시 알림을 한 채널에 두면 사용자가
  발동 알림을 끌 때 '공유 중' 표시까지 사라진다. 그건 원칙 2 위반이라 따로 두었다.
  상시 알림 채널 중요도를 LOW 가 아니라 DEFAULT 로 둔 것도 같은 이유다(LOW 면 기기에
  따라 알림 목록에서 접혀 눈에 안 띈다). 소리는 따로 껐다.
- **`stopWithTask="true"`.** 최근 앱 목록에서 앱을 밀어 치우면 공유도 멈춘다.
  기본값(false)이면 앱을 치운 뒤에도 수집이 이어진다. 상시 알림은 남으니 원칙 2를
  어기는 것은 아니지만, 앱을 치운 사용자는 멈추려는 뜻이었을 가능성이 높다고 봤다.
- **`geo:` URI 와 로캘.** `String.format` 으로 좌표를 만들면 로캘에 따라 소수점이
  쉼표가 되어 `geo:37,5665,126,978` 이 된다. 지도 앱이 좌표를 못 읽는다.
  `Double.toString` 을 쓰고 테스트를 달았다.
