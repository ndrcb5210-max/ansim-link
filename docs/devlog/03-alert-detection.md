# 3단계 — 재난문자 감지와 발동 규칙

작업일: 2026-10-25 · 브랜치: `feature/03-alert-detection`

## 한 일

### 분류기 (순수 Kotlin)

`domain/alert/` 에 안드로이드를 전혀 모르는 분류기를 만들었다. 입력은 패키지 이름·제목·본문·채널 ID,
출력은 문자 종류·재난 유형·신뢰도다.

- **문자 종류**는 제목으로 정한다. 비교하기 전에 **공백을 모두 지운다**(`AlertText.squeeze`).
  기기·안드로이드 버전에 따라 `긴급 재난문자` / `긴급 재난 문자` 처럼 띄어쓰기가 다른데,
  공백을 지우면 이 사본들이 한 문자열로 모인다. 한국어와 영어를 모두 본다.
- **재난 유형**은 본문 낱말로 정한다. 어휘는 행정안전부 재난구분 35종(`DisasterCategory`)까지
  가린 뒤 설정 화면용 12개(`DisasterType`)로 묶는다. 35종까지 가리는 이유는 발동 기록에
  ‘화재’와 ‘폭발’처럼 더 자세한 값을 남겨 두면 나중에 분류기를 고칠 때 근거가 되기 때문이다.
- 여러 개가 맞으면 지시문의 우선순위로 하나를 고른다.
  지진해일 > 지진 > 민방공 > 산사태 > 홍수 > 호우 > 태풍 > 산불 > 대설 > 한파 > 폭염 > 기타.
  같은 묶음 안에서는 선언 순서로 정한다(‘폭발’과 ‘화재’가 같이 있으면 ‘폭발’).
- **신뢰도**는 세 단계다. 제목과 유형을 다 가리면 ‘높음’, 제목만 맞으면 ‘보통’,
  제목을 못 맞히면 ‘낮음’. 발동 여부를 바꾸지는 않고 발동 기록 화면에만 보여 준다.
  감지가 어긋났을 때 ‘제목을 못 읽은 것인지, 유형을 못 가린 것인지’ 구분하려고 둔다.

단위 테스트 **78개**(분류기 54 + 규칙 엔진 24).
테스트에 쓴 재난문자 본문은 **전부 지어낸 예시**다. 실제 문장의 *형태*(발신 기관을 대괄호로 적고,
날짜·시각과 지역을 앞에 두고, 행동 요령을 뒤에 붙이는 틀)만 참고했고 특정 문자를 옮긴 것은 없다.
지역 이름은 `○○시` 로 가렸다. 그 사실을 `AlertClassifierTest` 머리말에 적어 두었다.
반대로 **제목 문자열은 지어내지 않았다.** 지시문에 적힌 AOSP CellBroadcastReceiver 의 제목과
그 띄어쓰기 변형, 영어 제목을 그대로 썼다.

### 발동 규칙 엔진

`TriggerEngine.decide()` 는 분류 결과 · 규칙 표 · 최근 발동 기록 · 지금 시각을 받아
발동 여부와 **이유**를 돌려주는 순수 함수다. 시계를 인자로 받으므로 테스트에서 시간을 돌릴 수 있다.

기본값은 위급·긴급 켬, 안전안내 끔이다. 실종경보문자는 지시문에 없어서 **끔**으로 두었다.
재난이 아니라 실종자를 찾는 문자라서 내 위치를 공유할 이유가 없다고 봤고, 사용자가 켤 수 있다.

판단 순서는 ① 종류 미상인가 → ② 종류 스위치가 켜져 있나 → ③ 유형 칩이 켜져 있나 →
④ 중복인가다. 규칙 검사를 중복 검사보다 앞에 둔 것은 기록에 남는 이유를 사용자에게 더 쓸모 있게
만들려는 것이다(‘중복이라 건너뜀’보다 ‘이 종류는 꺼 두셨습니다’가 행동으로 이어진다).

### 화면

- **감지 설정 안내**: 왜 알림 접근이 필요한지 → 무엇을 읽는지 → 무엇을 저장하지 않는지 →
  읽는 앱 목록 → 보장할 수 없는 점을 먼저 보여 주고, 그 **아래**에 ‘알림 접근 설정 열기’를 둔다.
  설명을 지나치지 않도록 버튼을 일부러 아래에 뒀다.
- **발동 규칙**: 4행 × 12열 표는 작은 화면에서 읽을 수 없다. 문자 종류마다 카드 하나를 두고
  스위치 + 유형 칩 12개로 바꿨다. 스위치를 꺼도 고른 유형은 그대로 남는다.
- **발동 기록**: 최근 50건. **발동하지 않은 것도 이유와 함께** 보여 준다.
  ‘재난문자를 받았는데 아무 일도 없었다’가 가장 답답한 상황이라서, 그 이유를 앱 안에서
  확인할 수 있어야 한다고 봤다.
- 디버그 전용 두 개: ‘테스트 재난문자 보내기’, ‘받은 알림 패키지 기록’.

화면은 모두 상태와 콜백만 받는다(2단계와 같은 방식). 시각은 ViewModel 이 미리 문자열로 만들어
넘긴다. 그래서 스크린샷이 기기 시간대나 찍는 시각에 따라 달라지지 않는다.

### 그 밖에

- 알림 접근 권한은 **런타임 권한 요청으로 받을 수 없다.** 사용자가 시스템 설정에서 직접 켜야 한다.
  앱이 할 수 있는 일은 ① 켜져 있는지 보고 ② 그 설정 화면을 열어 주는 것뿐이다.
- 발동하면 중요도 높은 알림 하나를 띄운다(공유 시작 / 안심 메시지만 보내기 / 닫기).
  **버튼은 지금 로그만 남긴다.** 4단계에서 연결한다. 지금 연결하면 동의 화면도, 포그라운드
  서비스도, 상시 알림도 없는 상태로 위치를 켜는 셈이라 CLAUDE.md 원칙 1·2 를 어기게 된다.
- 테스트 165개 통과(단위 144 + 스크린샷 21). `lint testDebugUnitTest assembleDebug` 통과,
  lint 오류 0개 · 경고 12개(전부 1·2단계에서 일부러 고정한 버전 관련 경고다. 새로 는 것은 없다).

## 고른 버전과 그 근거

1·2단계와 같은 방법으로 확인했다. AAR 의 `aar-metadata.properties` 로 `minCompileSdk` 를,
`classes.jar` 안 `META-INF/*.kotlin_module` 첫 16바이트로 Kotlin 메타데이터 버전을 직접 읽었다.
(Kotlin 2.2 컴파일러는 메타데이터 2.3.0 까지만 읽는다 — 2단계 참고.)

| 항목 | 고른 버전 | minCompileSdk | 메타데이터 |
| --- | --- | --- | --- |
| androidx.room | 2.8.5 | 34 | 2.1.0 |
| androidx.datastore:datastore-preferences | 1.3.0 | 34 | 2.2.0 |
| androidx.sqlite (room 이 끌고 온다) | 2.6.2 | 34 | — |
| KSP | 2.2.21-2.0.5 | — | — |

- **Room 2.8.5 가 최신인데 그대로 쓸 수 있었다.** 1·2단계에서 애를 먹은 `minCompileSdk=37`
  문제가 여기서는 없었다. Room·DataStore 는 Compose·lifecycle 만큼 빠르게 올라가지 않는다.
- **KSP 는 Kotlin 버전과 짝이 맞아야 한다.** `2.2.21-2.0.5` 가 Kotlin 2.2.21 용 최신이다.
  `room-compiler 2.8.5` 의 POM 은 `symbol-processing-api 2.0.10-1.0.24` 를 적고 있어서
  KSP2 에서 될지 확인이 필요했는데, 실제로 컴파일해 보니 문제없었다.
- **`room-ktx` 는 넣지 않았다.** Room 2.7 부터 코루틴 지원이 `room-runtime` 에 들어 있다.
  `room-runtime 2.8.5` 의 Gradle 모듈 메타데이터를 보면 `kotlinx-coroutines-core 1.8.1` 을
  직접 끌고 온다. DAO 가 `Flow` 를 돌려주는 데 추가 의존성이 필요 없다.

## 막힌 점

### 1. 알림 접근 권한의 진짜 위험은 ‘모든 알림이 보인다’는 것

이 단계에서 제일 오래 고민한 부분은 코드가 아니라 **무엇을 읽지 않을 것인가**였다.

알림 접근(`NotificationListenerService`)은 재난문자 앱의 알림만 주는 권한이 아니다.
**휴대폰에 뜨는 모든 알림**이 들어온다. 메신저 내용, 메일 제목, 은행 알림이 전부 지나간다.
그래서 리스너에서 제일 먼저 하는 일을 ‘허용 목록 검사’로 두고, 아니면 `extras` 를 **열지도 않고**
바로 돌아 나오게 했다.

```kotlin
if (!AlertPackages.shouldInspect(packageName, channelId, this.packageName, BuildConfig.DEBUG)) {
    if (BuildConfig.DEBUG && packageName != this.packageName) {
        scope.launch { detector()?.recordObservedPackage(packageName) }  // 패키지 이름만
    }
    return
}
val extras = statusBarNotification.notification?.extras ?: return   // 여기부터 내용을 읽는다
```

디버그 빌드의 ‘받은 알림 패키지 기록’도 **패키지 이름·횟수·마지막 시각만** 쌓는다.
제목·본문은 읽지 않는다. 채널 ID 는 패키지 검사에 필요해서 읽지만 허용 목록 밖이면 저장하지 않는다.

### 2. 테스트 알림이 자기 자신을 다시 읽는다

지시문은 “디버그에서는 자기 패키지를 허용 목록에 추가”하라고 했다. 그대로 하면 문제가 생긴다.
**발동했을 때 띄우는 ‘위치를 공유할까요?’ 알림도 우리 앱이 띄운 알림**이라서, 리스너가 그것을
다시 읽는다. 제목이 재난문자 제목이 아니니 발동하지는 않지만, 발동 기록에 ‘종류 미상’ 줄이
한 건씩 따라 붙어 기록이 더러워진다.

그래서 우리 앱 **전체**가 아니라 **테스트용 알림 채널 하나**(`ansim_debug_test_alert`)로 온
알림만 받아들이게 했다.

```kotlin
fun isDebugTestAlert(packageName: String, channelId: String?, selfPackageName: String, allowSelf: Boolean) =
    allowSelf && packageName == selfPackageName && channelId == DEBUG_TEST_CHANNEL_ID
```

`allowSelf` 에는 `BuildConfig.DEBUG` 를 넘긴다. 릴리스 빌드에서는 우리 앱의 알림을 아예 보지 않는다.

### 3. 언어별 사본은 본문 해시로 못 잡는다

지시문은 “같은 본문은 10분 안에 한 번만(해시)”이라고 했고 CLAUDE.md 는 거기에
“**언어별 사본이 와도** 한 번만”을 더한다. 그런데 한국어판과 영어판은 **본문이 다르다.**
해시로는 절대 같아지지 않는다.

그래서 중복 검사를 두 겹으로 두었다.

1. **같은 본문 해시** — 재난문자 앱이 같은 알림을 다시 게시하는 경우.
2. **같은 문자 종류 + 같은 재난 유형** — 언어별 사본, 그리고 문구만 조금 다른 재게시.

②에는 대가가 있다. 10분 안에 들어온 **다른** 지진 문자(여진 등)도 건너뛴다.
지금 단계에서 ‘발동’은 알림 하나를 띄우는 것이고 같은 알림을 겹쳐 띄우는 것이 더 나쁘다고 보고
이쪽을 골랐다. 종류가 올라가면(안전안내 → 긴급) 다른 문자로 보고 다시 발동한다.
4단계에서 공유 세션이 생기면 ‘이미 공유 중’ 상태가 ②의 역할을 대신할 수 있으니 그때 다시 본다.

본문이 없는 알림은 지문이 모두 `"empty"` 가 되므로 ①에서 제외한다.
그러지 않으면 본문 없는 알림이 서로를 전부 중복으로 만든다.

### 4. ‘유형 미상’을 어느 칸에서 찾을 것인가

Android 15 부터 OTP 로 판단된 알림은 내용이 가려져 온다
([공식 문서](https://developer.android.com/about/versions/15/behavior-changes-all):
“Android will stop untrusted apps that implement a `NotificationListenerService` from reading
unredacted content from notifications where an OTP has been detected.”).
그러면 본문이 비어 보이고 재난 유형을 가릴 수 없다.

문제는 **그때 규칙 표의 어느 칸을 볼 것인가**였다. 세 가지를 놓고 골랐다.

1. 발동하지 않는다 → 사용자가 ‘위급재난문자는 다 켰는데 왜 아무 일도 없었나’를 알 수 없다.
2. 무조건 발동한다 → 사용자가 끌 방법이 없다.
3. **‘기타’ 칸의 설정을 따른다** → 설정 화면에 보이는 칸이라 끄고 켤 수 있다.

3번을 골랐고 `DisasterType.ruleType` 에 적어 두었다. 발동 규칙 화면에도 그 설명을 한 줄 넣었다.

> **확인하지 못한 것(TODO):** 내용이 가려졌다는 것을 **알려 주는 공개 API 를 찾지 못했다.**
> 공식 문서는 ‘가려진다’는 사실만 적고 리스너가 받는 값의 모양은 적지 않는다.
> 지금은 ‘본문이 비어 있으면 유형 미상’으로 처리한다. 가려진 내용이 빈 문자열이 아니라
> 자리표시자 문구로 온다면 그 문구를 ‘기타’로 잘못 가릴 수 있다. 실기기 확인이 필요하다.

한편 **문자 종류를 모르는 경우**(‘새 경보’ 같은 묶음 알림)는 다르게 처리했다.
무엇인지 아예 모르는 알림으로는 발동하지 않는다(`TriggerReason.SeverityUnknown`).
규칙 표에 ‘종류 미상’ 행을 억지로 켜 두어도 발동하지 않는다는 테스트를 달아 두었다.

### 5. `Extreme Emergency Alert` 안에 `Emergency Alert` 가 들어 있다

영어 제목을 ‘포함’으로 비교하는데, 순서를 잘못 두면 위급재난문자가 긴급재난문자로 떨어진다.
enum 선언 순서(위급 → 긴급 → 안전안내 → 실종경보)로 먼저 맞는 것을 쓰게 하고 테스트를 달았다.

같은 이유로 묶음 알림 제목 목록에서 `Emergency alerts` 를 뺐다. 그 제목을 묶음으로 넣으면
`AlertSeverity.fromTitle` 이 먼저 ‘긴급재난문자’로 맞혀 버려서 서로 어긋난다.

### 6. lint 의 `MissingPermission` 은 helper 함수를 따라가지 않는다

권한 검사를 `canPostNotifications(context)` 로 빼 두고 `notify()` 앞에서 불렀더니 lint 가
그대로 오류를 냈다.

```
AlertNotifications.kt:108: Error: Call requires permission which may be rejected by user:
code should explicitly check to see if permission is available (with checkPermission)
or explicitly handle a potential SecurityException [MissingPermission]
```

lint 는 `notify()` 를 부르는 **같은 함수 안에 있는** `checkSelfPermission` 만 알아본다.
알림을 띄우는 곳을 `AlertNotifications.post()` 하나로 모으고 그 안에 검사를 그대로 적어서 풀었다.
경고를 숨기지 않고 구조를 바꾼 쪽이 맞다고 봤다. 어차피 알림을 띄우는 곳은 한 군데면 충분하다.

### 7. 낱말 하나가 다른 유형을 가로챈다

- `지진` 의 낱말에 `진도` 를 넣으려다 뺐다. **전남 진도군** 이름과 겹쳐서 진도군에 보내는
  아무 문자나 지진으로 잡힌다.
- `호우` 의 낱말에 `시간당` 을 넣으려다 뺐다. 대설 문자에도 ‘시간당 3cm’ 처럼 쓰여서,
  우선순위상 호우(6위)가 대설(9위)을 가로챈다.

둘 다 코드에 왜 뺐는지 주석으로 적어 두었다. 이런 것은 테스트로 미리 잡기 어렵고
실기기에서 실제 문자를 보면서 고쳐야 한다.

      추측으로 넣으면 엉뚱한 앱의 알림을 읽게 되므로 넣지 않았다.
      디버그 빌드의 ‘받은 알림 패키지 기록’ 화면으로 실기기에서 확인한 뒤 `AlertPackages.known`
      에 추가해야 한다. 그 전까지 삼성 기기에서는 감지되지 않을 수 있다.
- [ ] **실기기 확인을 하나도 못 했다.** 이 환경에는 기기도 에뮬레이터도 없다.
      리스너가 실제로 연결되는지, AOSP 재난문자 앱의 제목이 정말 저 모양인지,
      채널 ID 가 무엇인지 모두 확인하지 못했다. 분류기·규칙 엔진은 순수 Kotlin이라 단위
      테스트로 덮었지만, 리스너와 알림은 실기기에서 처음 검증된다.
- [ ] **알림 채널 ID 를 판단에 쓰지 않는다.** 분류기 입력으로 받아 기록만 한다.
      AOSP CellBroadcastReceiver 가 쓰는 실제 채널 ID 를 확인하지 못해서 추측으로 쓰지 않았다.
      실기기에서 확인하면 ‘제목을 못 읽었지만 채널로 보아 재난문자’ 같은 판단을 더할 수 있다.
- [ ] 내용이 가려진 알림을 알아보는 방법(위 ‘막힌 점’ 4번의 TODO).
- [ ] 발동 알림의 버튼 세 개는 로그만 남긴다 → 4단계.
- [ ] 홈 화면에 ‘마지막 감지’ 요약을 넣으면 좋겠다. 지금은 켜짐/꺼짐만 보여 준다.
- [ ] 자동 시작 모드(배경 위치)는 4단계다. 지금은 ‘한 번 눌러 시작’ 흐름의 **묻는 알림**까지만 있다.

      그렇게 두었다. 스키마를 바꿀 때 내보내기와 마이그레이션을 같이 넣어야 한다.
