## 한 일

### 고른 버전과 그 근거

1~4단계와 같은 방법으로 확인했다. AAR 의 `aar-metadata.properties` 로 `minCompileSdk` 를,
`classes.jar` 안 `META-INF/*.kotlin_module` 첫 16바이트로 Kotlin 메타데이터 버전을
직접 읽었다.

| 항목 | 고른 버전 | minCompileSdk | 메타데이터 |
| --- | --- | --- | --- |
| com.android.billingclient:billing | 9.1.0 | **파일 자체가 없음** | **없음**(순수 자바) |
| com.google.firebase:firebase-functions | 22.1.1 (BoM 34.19.0 이 정함) | 1 | 1.9.0 |
| (참고) billing-ktx | 9.1.0 | 없음 | **2.3.0** |

`billing` AAR 에는 `aar-metadata.properties` 가 **아예 들어 있지 않다.** 그래서
`minCompileSdk` 제약이 없다. `classes.jar` 안에 `kotlin_module` 도 없다 — 순수 자바
라이브러리라 2단계에서 애를 먹은 Kotlin 메타데이터 상한 문제와 무관하다. 매니페스트의
`minSdkVersion` 은 23 이라 우리 `minSdk 26` 에서 그대로 쓸 수 있다.

**`billing-ktx` 는 넣지 않았다.** 그쪽 `classes.jar` 에는 `kotlin_module` 이 하나 있고
메타데이터가 **2.3.0** 이다. 2.3.0 은 Kotlin 2.2 컴파일러가 읽을 수 있는 정확한 상한이라
(4단계의 `play-services-location` 과 같은 자리) 다음 버전에서 2.4.0 으로 올라가면 깨진다.
그리고 ktx 가 해 주는 것은 콜백 → suspend 변환뿐인데, 정작 까다로운 **연결 수명**은
그대로 남는다. 어차피 직접 다뤄야 해서 `CompletableDeferred` 로 감쌌다.

Play Billing 버전 정책도 확인했다. 2026-08-31 부터 새 앱·업데이트는 **8 이상**이어야
하고(요청하면 2026-11-01 까지 연장), 9.0.0 이 2026-05-19, 9.1.0 이 2026-06-18 에 나왔다.
9.1.0 이 지금의 안정 최신판이라 그것을 골랐다.

### Billing 8 에서 바뀐 것 두 가지

공식 릴리스 노트를 보고 맞췄다. 추측으로 썼으면 컴파일부터 깨졌을 것들이다.

1. `queryProductDetailsAsync` 리스너의 둘째 인자가 `List<ProductDetails>` 에서
   **`QueryProductDetailsResult`** 로 바뀌었다. 받아 오지 못한 상품도 같이 알려 준다
   (`getUnfetchedProductList`). 그 목록이 비어 있지 않으면 로그에 남긴다.
2. 인자 없는 `enablePendingPurchases()` 가 **삭제**됐다.
   `enablePendingPurchases(PendingPurchasesParams)` 를 써야 한다.

`enableAutoServiceReconnection()`(8.0 에서 들어왔다)도 켰다. 서비스가 끊겼을 때
라이브러리가 알아서 다시 붙으므로 `onBillingServiceDisconnected` 에서 직접
`startConnection` 을 다시 부르는 코드와 그 재시도 백오프가 필요 없어졌다.

### 프리미엄을 여는 근거는 한 곳뿐이다

이 단계의 중심 설계다. `users/{uid}.entitlement` **하나**만 본다.

```
Play 결제 성공 → 구매 토큰 → verifySubscription(서버) → Play Developer API
  → users/{uid}.entitlement 쓰기 → 앱이 Firestore 구독으로 읽음 → 프리미엄
```

앱이 끼어들 수 있는 자리를 전부 막았다.

- `BillingRepository` 인터페이스에 **프리미엄을 여는 함수가 없다.** 구매가 성공해도
  돌려주는 것은 구매 토큰뿐이다. 4단계에서 `ShareRepository` 에 FCM 발송 함수를
  두지 않은 것과 같은 생각이다.
- `EntitlementRepository` 에 **쓰는 함수가 없다.** 쓸 수 있는 코드를 두지 않는 것
  자체가 설계다.
- `verifySubscription` 의 **응답을 믿지 않는다.** 응답은 화면 안내 문구를 고르는 데만
  쓴다. 응답을 믿고 열면 중간에서 응답을 바꿔치기하는 것으로 프리미엄이 열린다.
- 보안 규칙이 `entitlement` 의 클라이언트 쓰기를 막는다. 앱 코드에 그 쓰기가 없다는
  것만으로는 모자라다 — APK 를 고친 사람은 우리 코드를 쓰지 않는다.

### 기간을 따로 보는 이유

`Entitlement.planAt()` 은 세 가지가 **모두** 맞아야 프리미엄을 준다.

1. 상태가 접근을 주는 상태인지,
2. 우리가 아는 상품인지,
3. `now < expiryTime` 인지.

3번이 핵심이다. 서버가 멈추면(배포를 안 했거나, RTDN 이 안 오거나, 함수가 죽어 있으면)
상태 값이 영원히 `active` 로 남는다. 기간을 같이 보면 **서버가 조용해질 때 저절로
무료로 돌아온다.** 줄이는 방향으로 틀리는 쪽을 골랐다.

대가도 적어 둔다. 기기 시계를 과거로 돌리면 만료된 뒤에도 3번을 통과한다. 상태가
`expired` 로 바뀌면 1번에서 막히므로 영구적이지는 않다. 기기 시계를 믿지 않으려면
신뢰할 수 있는 시간 출처가 필요한데 앱에는 없다. 반대 방향(시계가 앞서 있음)은
프리미엄이 일찍 꺼지는 쪽이라 안전하고 저절로 낫는다.

### 상태별로 접근을 줄지 — 문서를 따랐다

Play 구독 수명 주기 문서가 상태마다 정해 두었다. 여섯 줄짜리 표지만 하나라도
뒤집으면 바로 '돈 낸 사람이 못 쓰거나 안 낸 사람이 쓰는' 문제가 된다.

| 상태 | 접근 | 이유 |
| --- | --- | --- |
| 활성 | 준다 | |
| 해지(기간 남음) | **준다** | 이미 낸 기간이다. 해지를 눌렀다고 바로 끊으면 안 된다. |
| 유예 기간 | **준다** | 결제 수단을 고칠 시간이다. Play 가 `expiryTime` 을 늘려 준다. |
| 보류 | 안 준다 | 유예 기간이 지나도 결제가 안 됐다. '바로 막으라'고 문서가 못박았다. |
| 일시정지 | 안 준다 | 돈을 내지 않고 쓰지도 못하는 기간이다. |
| 대기·만료·회수 | 안 준다 | |

**모르는 상태는 막는다.** Play 에 새 상태가 생겼을 때 '모르니까 열어 준다'로 동작하면
안 된다. 앱과 서버 양쪽에 같은 판단을 둔 것도 일부러다 — 앱은 서버 값을 믿지만,
서버가 잘못된 상태를 써도 앱이 한 번 더 막는다.

### 요금제를 보는 곳이 다섯 군데였다

4단계까지 `Plan.Free` 가 다섯 군데에 하드코딩돼 있었다. 그룹 개수, 인원, 공유 시간,
유형별 메시지, 화면 표시. 거기에 각각 '서버에서 읽어 오기'를 적으면 **다섯 군데가
서로 다른 판정을 하게 된다.** 특히 '언제 무료로 떨어지는가'가 어긋나면 화면은
프리미엄인데 저장은 무료 한도로 되는 상태가 생긴다.

그래서 판정은 `Entitlement.planAt()` 하나, 그것을 부르는 곳은 `PlanProvider` 하나로
두었다.

**화면은 흐름을 구독하고, 동작은 그 순간 값을 다시 읽는다.**

```kotlin
// 화면: 흐름
val plan: StateFlow<Plan>
// 동작: 지금 값
suspend fun currentPlan(): Plan
```

`LocationShareService` 와 `SafetyMessageWorker` 가 `currentPlan()` 을 쓴다. 발동은 앱이
닫혀 있을 때 일어나고, 그때 프로세스는 방금 깨어난 상태라 구독 상태 흐름이 아직 첫
값을 못 받았을 수 있다. 초깃값인 무료를 쓰면 **돈을 낸 사람이 60분만 공유하게 된다.**

### 확인(acknowledge)은 검증 뒤에

Play 는 3일 안에 확인하지 않은 구매를 **자동으로 환불하고 취소한다.** 그래서 확인은
반드시 해야 하는데, 순서가 중요하다.

```
구매 → 서버 검증 → 확인(acknowledge) → entitlement 기다리기
```

확인을 먼저 하면 검증이 실패했을 때 '돈은 빠져나갔고, 프리미엄은 안 열렸고, 자동
환불도 안 되는' 가장 나쁜 조합이 된다. 검증을 먼저 하면 최악의 경우에도 Play 가
되돌려 준다.

확인을 **앱에서** 하는 것으로 정했다. 서버에서도 할 수 있지만 양쪽에서 하면 '서버는
확인했는데 앱은 그 사실을 모르는' 상태가 생기고 앱이 또 시도한다. 어느 쪽이든 3일
안에만 하면 되므로 한쪽에서만 한다.

그리고 결제 화면을 열 때마다 `queryPurchases()` 로 **확인하지 못한 구매를 줍는다.**
결제 직후 앱이 죽거나 네트워크가 끊기면 그런 구매가 남고, 그대로 두면 3일 뒤
환불된다.

### 결제 화면이 반드시 보여 주는 것

| 요구 | 어디에 |
| --- | --- |
| 가격 | Play 가 준 `formattedPrice` 를 **그대로** |
| 결제 주기 | '매월'(ISO 8601 `P1M` 을 읽어 만든다) |
| 자동 갱신 | '매월 자동 갱신됩니다. 해지할 때까지 결제가 이어지고…' |
| 무료 체험 전환 시점·금액 | '무료 체험 7일이 끝나면 ₩2,500이 자동으로 결제됩니다' |
| 해지 방법 | [구독 관리] → Google Play 구독 화면 |
| 약관·처리방침 | 화면 아래 링크 |

금액을 앱이 만들지 않는다. 통화 기호 위치·자리수 구분·소수점 유무가 나라마다 다르고,
화면에 적은 금액과 실제 청구 금액이 어긋나면 그대로 정책 위반이다.

**해지 방법을 결제하기 전에 보여 준다.** 결제한 뒤에만 보여 주면 '어떻게 그만두는지
모르고 결제하는' 상태가 된다. 해지 경로는 결제 화면·설정 > 구독·계정 삭제 세 군데에
두고 **같은 링크**를 쓴다(세 군데가 서로 다른 곳으로 가면 사용자가 그 경로를 못 믿는다).

### 가격을 못 받으면 버튼을 끈다

금액을 모르는 채로 결제 흐름을 띄우면 사용자가 얼마를 내는지 모르고 누른다.
그래서 버튼을 끄는데, **끄는 것으로 끝내지 않는다.** 이유 없이 꺼진 버튼만 보여 주면
'고장인가' 하고 생각한다.

이유를 다섯 가지로 나눴다. 네트워크, Play 스토어 문제, 구독 미지원, 상품 없음,
서버 설정 없음. 응답 코드(`BILLING_UNAVAILABLE(3)`)를 그대로 보여 줘도 사용자가 할 수
있는 일이 없기 때문이다. 다시 시도해 볼 만한 것(네트워크·알 수 없음)에만
[다시 시도] 를 준다 — 상품이 없는 것은 Play Console 쪽 문제라 다시 눌러도 달라지지
않는다.

### 비교표에서 무료를 깎지 않는다

재난문자 감지, 위치 공유, 제공 기록, 동의 철회·일시중지는 **무료에서도 똑같이 된다.**
그 사실을 비교표 아래에 적었다. 이 앱은 재난 상황에 쓰는 앱이고, 프리미엄이
'안전을 더 사는 것'처럼 읽히면 안 된다. 구독은 한도만 늘린다.

비교표의 숫자는 `PlanLimits` 에서 가져온다. 화면에 직접 적으면 한도를 고칠 때 화면
문구가 남아서 '화면에는 10명이라는데 9명에서 막힌다'가 된다.

### 서버 (`functions/`)

함수 두 개를 더했다. **배포하지 않았다**(Blaze 요금제 필요).

| 함수 | 하는 일 |
| --- | --- |
| `verifySubscription` | 구매 토큰을 `purchases.subscriptionsv2.get` 으로 확인하고 `users/{uid}.entitlement` 를 쓴다 |
| `onPlayNotification` | 실시간 개발자 알림(RTDN)을 받아 구독 상태를 다시 확인한다 |

4단계와 같이 판단은 `src/entitlement.ts` 의 순수 함수에 두고 `index.ts` 는 배선만
둔다. 그래서 **에뮬레이터도 네트워크도 없이** `node --test` 로 돌린다.

**알림 종류만 보고 Firestore 를 고치지 않는다.** 알림은 순서가 보장되지 않는다. 늦게
도착한 '갱신됨'으로 이미 해지된 구독을 되살리면 안 된다. 그래서 거의 모든 알림을
'지금 상태를 Play 에 다시 물어본다'로 보낸다. 회수·환불만 예외로 즉시 막는다 —
다시 물어보는 동안 열려 있는 틈을 두지 않는다('즉시 권한을 회수하라'는 문서 권고).

**서비스 계정 키를 만들지 않는 길을 기본으로 적었다.** 함수의 기본 서비스 계정을
Play Console 에 초대하면 키 파일이 아예 필요 없다. 그 길이 막혔을 때만 Secret Manager
를 쓴다. 저장소에는 어떤 키도 넣지 않았다(원칙 6).

### 구매 토큰을 문서 ID 로 쓰지 않는다

RTDN 에는 구매 토큰만 있고 uid 가 없다. 그래서 검증할 때 매핑을 남겨야 하는데,
토큰 자체를 문서 ID 로 쓰면 **색인·로그·오류 메시지에 그대로 남는다.** 구매 토큰은
그것만 있으면 Developer API 로 구독을 조회할 수 있는 비밀값이다.

SHA-256 을 ID 로 쓴다(`purchaseTokens/{sha256}`). 조회는 되면서 토큰은 남지 않는다.
같은 이유로 `obfuscatedAccountId` 에도 uid 를 그대로 넘기지 않고 SHA-256 을 넘긴다 —
그 값은 Play Console 주문 상세와 Developer API 응답에 그대로 보이고, uid 가 보이면
그것으로 Firestore 문서 경로를 알 수 있다.

### 가짜 결제 저장소 (디버그 전용)

Play Console 계정 없이 결제 화면의 흐름과 한도 적용을 볼 수 있게 했다. 상황 7가지를
고른다(무료 체험 있음/없음, 가격 미수신, 네트워크 오류, 사용자 취소, 결제 대기,
이미 구독 중).

**`app/src/debug/` 소스셋에 두었다.** `BuildConfig.DEBUG` 로 가르면 가짜 구현의 코드가
릴리스 APK 안에 들어가고, R8 이 지워 주기를 기대하는 것밖에 할 수 없다. 결제처럼
'없어야 하는 것이 있으면 바로 사고'인 곳에서는 기대가 아니라 보장이 필요하다.
소스셋에 없는 코드는 컴파일 대상이 아니라 들어갈 길이 없다. 내비게이션 등록 함수도
같은 이름으로 디버그·릴리스 양쪽에 두고 릴리스 쪽은 빈 함수로 두었다.

**가짜 결제로는 프리미엄이 열리지 않는다.** 보안 규칙이 `entitlement` 쓰기를 막기
때문이다. 그 제약을 일부러 남겼다 — 가짜 결제가 프리미엄을 열 수 있으면 그 경로가 곧
우회 경로이고, '디버그 빌드에만 있다'로는 안심할 수 없다(디버그 APK 도 돌아다닌다).
그래서 그 사실을 화면에 적어 두었다. 버그가 아니라 설계다.

확인한다.

## 막힌 점

### 1. 턴 한도로 한 번 끊겼다

위 머리말에 적었다. 4단계처럼 원인을 모르는 매달림이 아니라 분명한 한도였고,
단위 커밋 덕분에 잃은 것이 없었다.

### 2. `entitlement` 쓰기를 막는 규칙이 '일시중지'를 막을 뻔했다 — 또

4단계 '막힌 점' 2번과 **똑같은 함정**을 또 밟을 뻔했다. 처음에는 이렇게 쓰려고 했다.

```
allow write: if isSelf(userId) && !('entitlement' in request.resource.data);
```

틀렸다. `update` 의 `request.resource.data` 는 **쓰고 난 뒤의 문서 전체**다. 서버가
그 필드를 써 준 뒤에는 사용자가 자기 이름(`displayName`)을 바꾸려 해도 그 쓰기에
`entitlement` 가 (바뀌지 않은 채) 들어 있어서 거부된다. **구독하는 순간부터 자기
프로필을 하나도 못 고치게 된다.**

`create` 와 `update` 를 나눠서, create 에서는 '필드가 없어야 한다', update 에서는
`diff` 로 '바뀌지 않았는지'만 보게 고쳤다.

```
allow create: if isSelf(userId) && !('entitlement' in request.resource.data);
allow update: if isSelf(userId)
              && !request.resource.data.diff(resource.data)
                    .affectedKeys().hasAny(['entitlement']);
```

4단계에서 같은 것을 당하고 devlog 에 적어 두었는데도 또 밟을 뻔했다. 이번에는
규칙을 쓰기 **전에** 그 기록을 다시 읽어서 피했다. '막지 말아야 할 것'을 확인하는
테스트를 다섯 개 달았다(이름 바꾸기, 동의 기록 갱신, 계정 삭제, 내 상태 읽기,
푸시 토큰 쓰기).

### 3. 보류 상태에서 지난 날짜가 '다음 결제일'로 보였다

스크린샷을 찍다가 찾았다. 보류(on hold) 상태의 구독은 Play 응답에서 `autoRenewing` 이
**true 로 남아 있는데** 기간은 과거다. 그것만 보고 문구를 고르니

```
다음 결제일: 2026년 10월 20일   ← 오늘은 10월 25일이다
```

이렇게 나왔다. 지난 날짜가 미래 일처럼 보인다.

화면이 시계를 모르므로(2~4단계부터 지켜 온 규칙) ViewModel 이 `renewalDatePast` 를
계산해 넘기고, 화면이 '…에 기간이 끝났습니다'로 적게 고쳤다. **그림으로 찍지 않았으면
못 봤을 종류의 버그다** — 단위 테스트는 상태와 날짜를 따로 보니까 둘을 같이 읽었을 때
말이 되는지는 보지 않는다.

### 4. 인원 한도를 어느 쪽 요금제로 볼 것인가

그룹 인원 한도는 **그룹을 만든 사람의 요금제**로 정해져야 한다. 소유자가 프리미엄이면
10명까지 받아야 하는데, 들어가는 사람이 무료라고 3명에서 막으면 안 된다.

그런데 들어가는 사람은 **소유자의 구독 상태를 읽을 수 없다.** `users/{uid}` 는 본인만
읽는다(그리고 그것을 열 생각은 없다 — 남의 결제 상태를 보여 줄 이유가 없다).

그래서 한도를 **초대 코드를 만들 때** 막기로 했다. 코드를 만드는 사람이 곧 소유자이므로
그 순간에 보면 맞는 요금제로 판정된다. 규칙에는 요금제와 무관한 상한 10명만 둔다.

빈 자리가 남는다. 소유자가 코드를 10개 만들어 둔 뒤 구독을 해지하면 그 코드로
10명까지 들어올 수 있다. 상한 10명은 규칙이 막으므로 '프리미엄 한도를 공짜로 쓰는'
것까지는 되는데, 가족 몇 명이 쓰는 규모에서 그 구멍을 막으려고 서버 함수를 하나 더
두는 것은 과하다고 봤다. 아래 '남은 일'에 적어 두었다.

### 5. 참여 동의 문구의 '최대 몇 분'은 들어가는 사람 기준이다

4번과 헷갈리기 쉬운데 반대다. 참여 동의 화면의 '최대 ○분 동안 내 위치가 제공됩니다'는
**내가 공유할 때의 상한**이므로 들어가는 사람의 요금제로 봐야 한다. 위치정보법
제19조②의 '제공 기간'을 사실과 다르게 적으면 동의 자체가 어긋난다.

같은 화면에 두 종류의 요금제가 섞여 있는 셈이라, 어느 쪽인지 코드 주석에 적어 두었다.

### 6. 결제 결과를 상태 변환 안에서 처리하면 안 된다

처음에는 `combine` 안에서 `billingState.lastResult` 를 보고 검증을 시작했다. 화면이
다시 구독할 때마다(화면 회전, 탭 이동) **같은 결과를 또 처리한다.** 검증 요청이 두 번
가고 안내가 두 번 뜬다.

`init` 에서 한 번만 구독하고 값이 **바뀔 때만** 처리하게 고쳤다. 상태 변환 함수는
순수하게 두었다.

### 7. 그 밖에 고민한 것

- **`billing-ktx` 를 안 쓴 것.** 위 '고른 버전'에 적었다. 메타데이터 2.3.0 이 상한이고,
  어차피 연결 수명은 직접 다뤄야 한다.
- **콜백이 아예 안 오는 경우.** Play 스토어 프로세스가 죽으면 `startConnection` 의
  콜백이 오지 않는다. 그러면 결제 화면이 영원히 '불러오는 중'에 머문다. 20초 시간
  제한을 두고 '지금은 금액을 받을 수 없다 + [다시 시도]'로 간다.
- **연결을 `Mutex` 로 감쌌다.** 화면 두 개가 동시에 `refresh()` 를 부르면
  `startConnection` 이 두 번 불려 `DEVELOPER_ERROR` 가 난다.
- **구독 중인 사람에게 결제 버튼을 보여 주지 않는다.** 눌러도
  `ITEM_ALREADY_OWNED` 가 나고, 그 전에 '또 결제되나?' 하고 불안하게 만든다.
- **결제 취소에 오류 색을 쓰지 않는다.** 아무 문제가 없는데 빨간 글씨로 적으면 겁을
  준다. `PaywallNotice.isError` 로 갈랐다.
- **유예 기간과 보류의 문구를 나눴다.** 보류는 이미 프리미엄이 꺼진 상태다. 같은
  문구를 쓰면 '지금 쓸 수 있나'를 알 수 없다.
- **계정 삭제를 구독 중이어도 막지 않는다.** Google Play 계정 삭제 정책 때문이다.
  대신 '계정을 삭제해도 구독은 해지되지 않는다'를 적고 Play 링크를 둔다. 규칙
  테스트에도 그 경우를 달았다.
- **필드 이름을 문자열로 못박는 테스트.** 앱·서버·규칙 세 군데가 같은 이름을 쓰는데
  한쪽만 고치면 조용히 틀린다(앱이 `unknown` 으로 읽고 프리미엄을 주지 않는다 —
  예외도 로그도 없다). 이름을 바꾸면 빨간불이 켜지게 해 두었다.

## 실제 결제 시험에 필요한 절차 (Play Console)

이 연재에는 Play Console 계정이 없어서 **하나도 해 보지 못했다.** 필요한 순서를
정리해 둔다. 자세한 명령은 `functions/README.md` 의 '구독 검증 설정'에 있다.

### 1. Play Console 에 앱을 만든다

Play Console 에서 앱을 만든다(패키지 이름 `io.github.ndrcb5210max.ansimlink`).

여기서 **처음에 잘못 알았던 것을 적어 둔다.** '사이드로드한 APK 로는 결제가 안 되니
내부 테스트 트랙에 AAB 를 올려야 한다'고 적었다가, 공식 문서를 확인하고 틀린 것을
알았다.

> License testers can bypass this check, meaning you can sideload apps for testing,
> even for apps using debug builds with debug signatures without the need to upload
> to the new version of your app.
> — developer.android.com/google/play/billing/test

**라이선스 테스터로 등록한 계정은 그 검사를 건너뛴다.** 디버그 서명으로 사이드로드한
빌드로도 결제 흐름을 돌릴 수 있고, 새 버전을 올릴 필요도 없다. 조건은 두 가지뿐이다.

- 패키지 이름이 Play Console 에 만든 앱과 같을 것,
- 그 Google 계정이 해당 Console 계정의 **라이선스 테스터**일 것.

즉 이 연재에서 가장 큰 벽은 '트랙에 올리기'가 아니라 **Play Console 계정 자체**다.
Console 계정만 있으면 지금 빌드 그대로 시험할 수 있다.

(라이선스 테스터가 **아닌** 계정에서는 여전히 Play 에서 설치한 앱이어야 한다. 그때는
내부 테스트 트랙에 서명된 AAB 를 올리고 테스터 링크로 설치한다. 릴리스 서명은
6단계에서 환경 변수로 넣는다.)

### 2. 구독 상품을 만든다

Play Console > 수익 창출 > 구독.

- 상품 ID: **`premium_monthly`** — 앱의 `SubscriptionCatalog.PREMIUM_MONTHLY` 와 글자
  하나까지 같아야 한다.
- 기준 요금제: 월 자동 갱신. 가격은 Console 에서 정한다(앱에 금액을 적지 않는다).
- 무료 체험을 둘 거면 그 기준 요금제의 **혜택(offer)** 으로 만든다. 앱은 받을 수 있는
  혜택 중 가장 유리한 것을 골라 보여 준다.
- **상품을 활성화한다.** 초안 상태면 조회되지 않는다.

### 3. 라이선스 테스터를 지정한다

Play Console > 설정 > 라이선스 테스트에 계정을 넣는다. **실제 결제 없이** 결제 흐름을
끝까지 돌릴 수 있고, 1번에 적은 대로 사이드로드한 빌드로도 된다.

테스트 구독은 **주기가 크게 짧아진다.** 이 표가 이 단계에서 가장 쓸모 있는 정보다 —
해지·유예 기간·보류·만료까지 하루 안에 다 볼 수 있다는 뜻이기 때문이다.

| 실제 주기 | 테스트 갱신 주기 |
| --- | --- |
| 1주 · 1개월 | 5분 |
| 3개월 | 10분 |
| 6개월 | 15분 |
| 1년 | 30분 |

| 기능 | 테스트 기간 |
| --- | --- |
| 무료 체험 | 3분 |
| 유예 기간 | 5분 |
| 보류(account hold) | 10분 |
| 일시정지 1개월 | 5분 |

테스트 구독은 **최대 6번** 갱신한 뒤 자동으로 끝난다(무료 체험·소개 가격 기간은
세지 않는다). 그래서 '만료되면 무료로 돌아오는지'를 기다려서 볼 수 있다.

서버 응답의 `testPurchase` 필드로 테스트 구매인지 알 수 있다. 로그에 남기고 있다.

### 4. Play Developer API 자격 증명

`functions/README.md` 의 **방법 A** 를 권한다. Play Console 과 Cloud 프로젝트를
연결하고, Cloud Functions 의 기본 서비스 계정 이메일을 Play Console > 사용자 및
권한으로 초대해 '재무 데이터 보기' 권한을 준다. **키 파일이 아예 필요 없다.**

권한이 바로 먹는지 시간이 걸리는지는 **확인하지 못했다**(Console 계정이 없다).
권한 전파 지연을 다룬 공식 문서를 찾지 못해서 추측으로 적지 않는다. 처음에 403 이
나면 권한 설정부터 다시 보되, 조금 기다렸다 다시 해 보는 것도 같이 해 볼 일로 남긴다.

### 5. 실시간 개발자 알림

1. Pub/Sub 주제 `play-billing-notifications` 를 만든다
   (`src/index.ts` 의 `PLAY_NOTIFICATION_TOPIC` 과 같은 이름).
2. 그 주제에 `google-play-developer-notifications@system.gserviceaccount.com` 에게
   **Pub/Sub 발행자** 권한을 준다.
3. Play Console > 수익 창출 설정 > 실시간 개발자 알림에 주제 전체 이름을 적는다.
4. 같은 화면의 **'테스트 알림 보내기'** 로 배선을 확인한다. 테스트 알림에는 구매
   토큰이 없어서 함수는 '처리하지 않는다'를 기록하고 끝난다 — 그 로그가 보이면
   트리거가 맞는 것이다.

### 6. 시험할 순서

테스트 주기가 짧아서(3번 표) 아래를 한두 시간 안에 다 돌 수 있다.

1. 결제 화면에서 가격이 보이는지. 안 보이면 상품 ID·활성화 여부·라이선스 테스터
   등록을 되짚는다(1·2·3번).
2. 구독 → `verifySubscription` 로그 → `users/{uid}.entitlement` 문서 확인.
3. 앱에서 프리미엄 한도가 열리는지(그룹 3개, 공유 180분 칩, 유형별 메시지 입력란).
4. Play 구독 화면에서 해지 → 알림 수신 → 상태가 `canceled` 로 바뀌는지.
   화면 문구가 '해지 예약됨 · ○○까지 쓸 수 있습니다'로 바뀌는지.
5. 그대로 두고 갱신 주기(5분)가 지나기를 기다려 `expired` → 한도가 무료로 돌아오는지.
   최대 6번 갱신한 뒤 자동으로 끝나므로 기다리면 반드시 이 상태가 된다.
6. 환불(Play Console > 주문 관리) → 즉시 `revoked` 가 되는지.
7. 결제 수단을 일부러 실패시켜 유예 기간(5분) → 보류(10분)까지 가 보고, 화면 문구가
   두 상태에서 다르게 나오는지('막힌 점' 3번에서 고친 자리다).

## 남은 일

- [ ] **실기기·실결제 확인을 하나도 못 했다.** Play Console 계정이 없다. 결제 흐름,
      가격 표시, 무료 체험 전환, 해지·환불 반영은 모두 위 절차를 밟은 뒤에 처음
      검증된다. 순수 Kotlin·TypeScript 부분(상태 판정, 혜택 고르기, 주기 읽기, 문서
      만들기)은 단위 테스트로 덮었지만, Billing 라이브러리와 Play 의 실제 응답은
      확인하지 못했다.
- [ ] **Cloud Functions 를 여전히 배포하지 못했다.** 4단계와 같다. 배포하지 않으면
      `verifySubscription` 이 없으므로 **프리미엄이 절대 열리지 않는다.** 지금 앱은
      결제까지는 가고 검증에서 '확인이 늦어지고 있다'에 머문다. 그 동작 자체는 맞게
      만들었지만(열어 주지 않는다) 실제로 그 상태가 되는지는 배포해 봐야 안다.
- [ ] **초대 코드를 미리 만들어 두고 해지하는 구멍**('막힌 점' 4번). 소유자 기준으로
      인원을 막는 서버 함수를 두면 닫힌다. 가족 몇 명 규모에서는 과하다고 보고 미뤘다.
- [ ] **구독 복원 경로가 약하다.** 기기를 바꾸면 Play 에는 구독이 있는데 우리
      `entitlement` 는 비어 있다. [구독 상태 다시 확인] 으로 되살릴 수 있게 해 두었지만,
      사용자가 그 버튼을 찾아야 한다. 로그인 직후 한 번 자동으로 훑는 편이 낫다.
- [ ] **`purchaseTokens` 매핑을 지우지 않는다.** 계정을 삭제해도 그 문서가 남는다.
      uid 만 들어 있어 쓸모는 없지만, `AccountDeleter` 가 같이 지워야 깔끔하다.
      (문서 ID 가 토큰 해시라서 uid 로 찾으려면 질의가 필요하다 — 색인이 든다.)
- [ ] **가격 인상 알림(in-app messaging)을 쓰지 않는다.** Billing 9.0 에 들어온 기능인데
      가격을 올릴 계획이 없어서 넣지 않았다.
- [ ] **연간 상품이 없다.** 월 구독 하나뿐이다. `SubscriptionCatalog.PREMIUM_PRODUCT_IDS`
      를 집합으로 둔 것이 그 자리다.
- [ ] 1~4단계부터 남은 일(다크 테마 스크린샷, `createComposeRule()` 이전, 구성 캐시,
      `compileSdk 37` 올리기, 삼성 재난문자 앱 패키지 이름, Room 스키마 내보내기,
      FCM 토큰 등록 시점, `cleanupExpiredLocations` 페이지 처리, 공유 시간 연장)은
      그대로 남아 있다.
